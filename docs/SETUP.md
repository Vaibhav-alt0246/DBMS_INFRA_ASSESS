# Current development setup

> **2026-11-14 security/workflow update:** Configure per-user bearer credentials before using the console/API. Apply the versioned migration for existing databases, and run the scheduled worker for alerts/search. [Current operational instructions](OPERATIONS.md) supersede the earlier unauthenticated and per-search indexing examples below.
Use PostgreSQL 14+, Python 3.11+ and Node.js 20.9+. The frontend uses Next.js 16 and React 19. PostgreSQL owns operational data; local persistent Qdrant is a rebuildable index. Docker is not required.

## 1. Python and configuration

From the repository root, on Windows PowerShell:

```powershell
py -3.13 -m venv .venv
& .venv/Scripts/python.exe -m pip install -r backend/requirements-dev.txt
Copy-Item .env.example .env
```

On macOS/Linux:

```bash
python3 -m venv .venv
.venv/bin/python -m pip install -r backend/requirements-dev.txt
cp .env.example .env
```

Edit `.env` to match your PostgreSQL host, port, database, username and password. Alternatively set `DATABASE_URL`. Settings load the root `.env` automatically; exported environment variables take precedence. Relative `QDRANT_PATH` values resolve from the repository root. Keep credentials out of Git.

## 2. PostgreSQL

Start your PostgreSQL service and verify the database identity before changing data:

```bash
psql -X -h localhost -U YOUR_USER -d infraassess_test -c "SELECT current_database(), current_user;"
```

For a **new empty database only**, create it and apply the installer:

```bash
createdb -h localhost -U YOUR_USER infraassess_test
psql -X --set ON_ERROR_STOP=1 -h localhost -U YOUR_USER -d infraassess_test -f database/install.sql
```

The installer applies schema, baseline seed, triggers, views, functions, procedure and additive synthetic incidents in that order. The baseline seed must precede the completion trigger because it contains a historical completed work order. The installer does not drop existing tables; do not use it to update an existing installation. It is intended for an empty database, not a reset operation.

On an existing project database, inspect installed objects first. Apply only the missing scripts. The function/procedure/view/trigger scripts can be rerun; `schema.sql` cannot. `demo_incidents.sql` preserves existing records.

## 3. Index and run

On Windows, from the root:

```powershell
& .venv/Scripts/python.exe -m vector_db.cli index
& .venv/Scripts/python.exe -m vector_db.search_evaluation
& .venv/Scripts/python.exe -m uvicorn backend.app.main:app --port 8000
```

On macOS/Linux substitute `.venv/bin/python` for `.venv/Scripts/python.exe`.

The first embedding operation downloads the configured Sentence Transformers model. Keep one backend worker when using local Qdrant. Stop the backend before running any separate Qdrant CLI or evaluation process against the same storage path.

In another terminal:

```bash
cd frontend
npm ci
# Optional: copy .env.example to .env.local to change the API URL.
npm run dev
```

Open `http://localhost:3000`; interactive API documentation is at `http://localhost:8000/docs`. CORS defaults to `http://localhost:3000`, configurable with `FRONTEND_ORIGIN`.

## Current behavior

- PATCH accepts only changed fields and supports explicit null for nullable columns. Required fields cannot be set to null; unknown fields are rejected.
- API timestamps must include a timezone (`Z` or an explicit offset). Status/outcome values, nonblank text, positive IDs, database column lengths and numeric precision are validated before SQL. Money uses exact decimals with at most two fractional digits; sensor readings allow four.
- Work-order completion uses `POST /api/work-orders/{id}/complete`, which calls `sp_complete_work_order`. Generic create/update cannot transition an open order to `COMPLETED`.
- Status checks and updates share a row-locked transaction. Completed/cancelled work orders cannot be reopened through PATCH. Completion locks its target before reading the procedure's identifier.
- Alerts are generated by database workflows. Their API supports list, get and status update. Audit history is read-only.
- Management pages paginate in batches of 25. Switching resources clears the previous form and selection; saves clear stale details.
- Date/time form controls display local time and submit ISO timestamps with an explicit timezone.
- Date/time edits retain seconds and milliseconds. Unchanged API timestamps pass through with their original PostgreSQL microseconds when other fields are edited. Superseded list/search requests are cancelled and late responses are ignored.
- Each semantic API search refreshes changed incident documents and removes deleted incident IDs before retrieval. Unchanged documents are not re-embedded. Component/category descriptions and work-order/maintenance resolution changes are included in the refresh. This full source scan suits the demo dataset; a larger deployment should use a durable change queue.
- Concurrent API operations serialize access to local Qdrant and reuse one loaded embedding model. Health checks do not download or initialize the embedding model; the vector health indicator checks collection access/configuration, not retrieval quality.
- Changed incident vectors are embedded/upserted in batches of 64 and stale IDs deleted in batches of 256. Index synchronization still scans the source documents and point hashes; these changes bound transient vector allocations, not total data size or scan latency.
- PostgreSQL connection attempts default to a five-second timeout, configurable through `PGCONNECT_TIMEOUT` or the explicit database URL. Unavailable database reads/mutations return a JSON 503. Health probes report vector search as `busy` rather than waiting on an active index/model operation.

## Checks

From the root on Windows:

```powershell
& .venv/Scripts/python.exe -m pytest -q backend/tests vector_db --basetemp .pytest_tmp
git diff --check
```

From `frontend`:

```bash
npm test
npm run typecheck
npm run build
npm audit --omit=dev
```

Browser regressions use a production build and isolated mocked API responses:

```bash
# Needed if a supported Windows Edge installation is not available:
npx playwright install chromium
npm run test:e2e
```

The runner starts and stops its own frontend on port 3100. It covers request races, edit/refresh/detail synchronization, timestamp precision, pagination after deletion, duplicate-save protection, validation errors, keyboard focus and mobile navigation. This does not require PostgreSQL, but does not verify database behavior.

For a synthetic indexing allocation benchmark, run `python -m scripts.benchmark_indexing` from the root. It compares an all-at-once batch with batches of 64 using generated vectors and a non-persistent store; no model downloads or database changes occur.

With PostgreSQL available, run each SQL test using `psql -X --set ON_ERROR_STOP=1 -d infraassess_test -f FILE`, supplying the correct host/user. Test files are `database/constraint_tests.sql`, `database/trigger_tests.sql`, `database/advanced_sql_tests.sql` and `database/transaction_tests.sql`. They expect the original baseline records to remain unchanged. Run `database/demo_verification.sql` to inspect dataset counts, then stop FastAPI before index/status/evaluation commands. See `TRANSACTION_CONCURRENCY_LAB.md` for the two-session locking demo.
